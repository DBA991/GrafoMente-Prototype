*From conceptual graph to working code — architecture, implementation, and limits of a real system*

*Fourth article in a series born from conversations with AI systems — written by an outside observer*

## A methodological preface

The three previous articles built a hypothesis in layers. The first introduced the philosophical foundation and the proposal of an AI that navigates concepts instead of compressing text. The second developed the architecture — prototypical graph, two-layer composite symbols, progressive fetch by instances. The third imagined how to apply it to code generation, identifying available technologies and still-open points.

This fourth article does the riskiest thing: it writes code.

This is not a production system. It is a working prototype that implements the principles described in the three previous articles in concrete, testable form. The code is written to be readable, not optimized. The domain coverage is deliberately small — twelve nodes, an Express + Node.js stack — because a small, precise domain shows the structure better than a large, approximate one. The goal is not to demonstrate that the system scales: it is to demonstrate that the mechanism works.

The complete code is available attached to this article.

## The graph: data structures

The most important implementation choice concerns the structure of the node. Each node has two separate layers, implemented as distinct Python dataclasses, with an authority hierarchy made explicit in the code.

```python
import uuid

@dataclass
class StableLayer:
    uuid: str            # machine primary key — never modifiable
    node_id: str         # human primary key — e.g. "express.middleware"
    label: list             # array of categorizations — updated in batch with centroid
    node_type: str          # "function" | "class" | "object" | "method"
    signature: str          # full typed signature
    docstring: str          # official documentation
    source_ref: str         # e.g. "github.com/expressjs/express@4.18.2"
    hierarchy_path: list    # e.g. ["express", "Router"]
    semantic_field: str     # primary semantic area
    intersections: list     # semantic fields this node can intersect with
    relations: list         # structural edges — referenced by destination node UUID
    prototypicality: float  # Rosch typicality weight (1.0 = center of the field)
    synonyms: list          # vocabulary for query translation
    keywords: list          # additional keywords

def make_stable_layer(node_id: str, **kwargs) -> StableLayer:
    """Builds a node with a UUID automatically generated at creation."""
    return StableLayer(uuid=str(uuid.uuid4()), node_id=node_id, **kwargs)
```

### UUID and node_id: two identifiers, two directions

The stable layer contains two identifiers that work together, not one replacing the other.

**`uuid`** is the system's operational key downward — toward the machine. It is automatically generated at node creation and is never modified or reassigned. Every internal operation uses the UUID: navigation during the fetch, resolution of structural relations, episodic layer updates, writing to and reading from disk. Relations in the `relations` field reference the destination node by UUID, not by label. The same applies to episodic links. If a node is renamed, moved in the hierarchy, or its signature is updated, the UUID remains stable — and all connections referencing it remain valid without any migration. Dedicated parsers and supervision systems accessing the graph from outside receive the UUID as the access key: the reference is always unambiguous, even across different versions of the graph or between distinct graphs.

**`node_id`** is the key exposed upward — toward the human. It is a readable, meaningful identifier (`"express.middleware"`, `"js.date"`, `"node.fs"`) that the human uses to build vocabularies, write queries, add instances manually, and inspect the graph in the interface. It is also used in the query-to-instances translation vocabulary, where each term is mapped to the UUID of the corresponding node through the `node_id` as an entry point. In logs and in the abandoned paths panel, paths are shown as `"express.middleware → express.request"` — human-readable labels, not UUIDs — because that panel is intended for the human. The `node_id` does not need to be globally unique (two different graphs may have a node `"app.init"`), but it must be unique within the graph in use.

**`label`** is the third identifier in the stable layer, and it is structurally different from both. It is not a string but an **array of categorizations** — the set of semantic contexts in which the node has been activated during use. A node born with `label: ["os"]` that is subsequently called in queries relating to `component` and `filesystem` will have, after the next batch update, `label: ["os", "component", "filesystem"]`. This accumulation is not cosmetic: the `label` array is what makes the node *determinable* — it records what the node has proven to be across different contexts of use, and it is precisely the intersection of those categorizations that defines the node's field. A node active in many distinct contexts has a broad field; one consistently activated in a single context has a narrow, well-defined one. The `label` is therefore not a description assigned at creation: it is a characterization that emerges from use and is made explicit in the stable layer during the periodic batch update.

The two identifiers therefore have distinct domains of validity: UUID is the key for internal consistency over time; `node_id` is the key for external intelligibility to the human. Neither is reducible to the other.

```python
@dataclass
class EpisodicLink:
    target_uuid: str          # UUID of the connected node — stable key over time
    intersection_field: str   # semantic area in which they met
    link_nature: str          # "direct" | "mediated" | "external_bridge"
    mediator_uuid: str        # if mediated, UUID of the intermediate node
    use_count: int = 1        # how many times this connection has been activated
```

The episodic layer accumulates contextual connections during use. Each link references the connected node by `target_uuid` — not by `node_id` — because the episodic layer must remain valid over time: if a node's label is corrected, the link does not break. When the fetch traverses an episodic link, it reads the `target_uuid`, accesses the node directly, and immediately obtains the signature, semantic field, and relations. The `use_count` is the counter that governs pruning: connections never reused decay during periodic maintenance, frequent connections are promoted to the stable layer. The `prune(min_use_count)` method is exposed as an API endpoint and is called explicitly by the human, not automatically.

The authority hierarchy — graph > stable layer > episodic layer — is not written as an abstract rule: it is structural in the code. The episodic layer cannot modify the stable layer; the stable layer cannot modify the graph. Promotion operations (from episodic to stable, or from stable to graph) are manual.

## Query → instances translation

The translation is intentionally symbolic and simple. The graph's nodes are static and finite; each node has an associated controlled vocabulary of terms, synonyms, and keywords. The mapping occurs in three steps: exact lookup, fuzzy-prefix lookup, expansion by semantic field.

```python
def translate(self, query: str, graph: ConceptGraph) -> list[str]:
    """Returns a list of UUIDs of the nodes identified as instances of the query."""
    tokens = self._tokenize(query)
    found_uuids = []

    # 1. Exact lookup — _term_map maps terms → UUIDs
    for token in tokens:
        if token in self._term_map:
            for uuid in self._term_map[token]:
                if uuid not in found_uuids:
                    found_uuids.append(uuid)

    # 2. Fuzzy-prefix: pattern from the term, applied to the query token
    if not found_uuids:
        for token in tokens:
            for pattern, uuids in self._fuzzy_patterns:
                if pattern.match(token):
                    for uuid in uuids:
                        if uuid not in found_uuids:
                            found_uuids.append(uuid)

    # 3. Expansion by semantic field — _field_map maps fields → UUIDs
    if not found_uuids:
        for token in tokens:
            for field, uuids in self._field_map.items():
                if token in field:
                    found_uuids.extend(uuids)

    return found_uuids
```

Step 2 deserves a note on the direction of matching. Patterns are built from **vocabulary terms** — `^.{0,3}<term>.*$` — and applied to **query tokens**, not the other way around. This distinction is substantial: the vocabulary defines the concepts; the query uses the variants with which a user may express them. The term `log` in the vocabulary produces the pattern `^.{0,3}log.*$`, which matches `logging`, `logga`, `loggare`, `re-log`, `prelogging` as query tokens — neologisms, loan words, and morphological variants are captured without having to list them explicitly in synonyms. Applying the same query token `logga` in reverse — searching for `logga` as a substring in vocabulary terms — would find nothing, because `logga` does not appear in any term. The maximum 3-character prefix rule limits noise: `catalog` (prefix `cata`, 4 characters) does not match `log`, while `dialog` (prefix `dia`, 3 characters) does — and this is the correct behavior, because `dialog` is semantically closer to `log` than `catalog` is.

Patterns are pre-compiled in `build_from_graph()` and stored in `_fuzzy_patterns` as a list of `(pattern, [uuid...])`. They are not recompiled on every query: the compilation cost is paid once, at startup or after each modification to the graph. Terms shorter than 3 characters are excluded from pre-compilation because they would produce overly noisy patterns.

The result of the translation is a list of UUIDs. For the query *"write an Express middleware that logs method, URL, and timestamp,"* the system correctly identifies nine instances — including `js.date` via fuzzy-prefix (`logga` → `log`) — visible to the user as `express.middleware`, `express.app`, `express.router`, `express.request`, `express.response`, `express.next`, `express.error_handler`, `express.json_middleware`, `js.date`. The result is shown to the user before the fetch; the user can remove non-pertinent instances or add them manually by `node_id` (the interface translates to UUID before proceeding).

This human confirmation step — a dedicated endpoint (`/query/translate`) that precedes the fetch — is the translation into code of the structural control principle: the system does not start navigation without the human having validated the starting point.

## The progressive fetch

The fetch is the heart of the system. It implements the dual stopping criterion: exhaustion of instances *and* exhaustion of pertinent paths starting from those instances.

```python
def _traverse(self, node_uuid, depth, query_tokens, instance_uuids,
              pool, visited, abandoned, new_links):
    """
    Recursive traversal of the graph by UUID.
    node_uuid: UUID of the current node.
    instance_uuids: set of UUIDs of the initial instances — the stopping criterion.
    pool: collects the UUIDs of pertinent nodes found.
    visited: set of already-evaluated UUIDs — prevents re-exploration.
    """
    if depth >= self.max_depth:
        return

    node = self.graph.get_node_by_uuid(node_uuid)  # access by UUID
    candidates = self._get_candidates(node, instance_uuids)
    # candidates: list of (candidate_uuid, score, link_source)

    for candidate_uuid, score, link_source in candidates:
        if candidate_uuid in visited:
            continue

        candidate_node = self.graph.get_node_by_uuid(candidate_uuid)
        # path_label uses node_id as a human-readable alias for logs and UI
        path_label = f"{node.stable.node_id} → {candidate_node.stable.node_id}"

        if self._is_relevant(candidate_node, query_tokens):
            pool.append(candidate_uuid)
            visited.add(candidate_uuid)
            self._traverse(candidate_uuid, depth + 1, ...)
        else:
            abandoned.append(path_label)
            visited.add(candidate_uuid)  # do not explore further
```

Every path is evaluated by UUID. The `get_node_by_uuid` method is the access key to the graph: it receives a UUID and returns the complete node with both layers. `node_id`s appear only in `path_label`s intended for logs and the interface — the "Abandoned paths" panel shows human-readable labels, not UUIDs, because it is a panel for the human.

If the candidate node is relevant to the query — in its semantic field, any entry in its `label` array, synonyms, or keywords — it is included in the pool and the traversal continues from it. Otherwise it is marked as abandoned and added to `visited`, preventing it from being re-explored from another path. The system never explores the entire graph: it explores only the paths that the instances open and that the query makes pertinent.

Relevance is evaluated using the same fuzzy-prefix mechanism used in translation: a node is relevant if at least one term from its semantic field, any entry in its `label` array, or its keywords matches a query token with the pattern `^.{0,3}<term>.*$`. This is necessary for consistency with the translation phase — a node reached through navigation must be recognizable as pertinent using the same criteria by which it would have been found directly. Without this extension, the fuzzy-prefix in translation would have a partial effect: `logga` would find `js.date` as an initial instance, but `js.console` — reachable from `js.date` via a structural relation — would be discarded during traversal because its terms (`console`, `log`, `output`) do not exactly match the token `logga`. With fuzzy in `_is_relevant`, the term `log` in `js.console`'s keywords matches `logga` and the node enters the pool.

Episodic links are used as shortcuts: if a node already has an `EpisodicLink` in its episodic layer with a pertinent `target_uuid`, that link is used with a relevance bonus proportional to the `use_count`, without having to rediscover the connection through structural traversal. New connections that emerge during the fetch are recorded in the episodic layer at the end of navigation, each with the `target_uuid` of the connected node.

## The structured RAG

The ordered pool is serialized into a structured textual format that preserves hierarchy, signatures, and relations:

```
=== STRUCTURED CONTEXT (conceptual graph) ===
Query: write an Express middleware that logs method, URL, and timestamp
Activated instances: express.middleware, express.app, ...

[1] middleware (function)
    Hierarchy: express > middleware
    Signature: (req: Request, res: Response, next: NextFunction) => void
    Field:     middleware
    Doc:       A middleware function has access to the request object...
    Relations: receives:express.request, receives:express.response, calls:express.next
    Source:    github.com/expressjs/express@4.18.2

[2] req (Request) (object)
    Hierarchy: express > Request
    ...
=== END CONTEXT ===
```

This is not raw text: it is a context in which the structure of the problem is partially resolved before the language model receives it. The LLM does not need to infer what `req` or `next` are — their signature and relation to the middleware are provided. The space for statistical invention is structurally reduced.

## The LLM connector: local and remote

The linguistic layer supports two modes, configurable from the interface without touching the code:

**Local via Ollama**: sends the RAG to the local model (`deepseek-coder`, `codellama`, or any other installed model) via the Ollama API on `localhost:11434`. No API keys required, works offline, suitable for experimentation.

**Remote via OpenAI-compatible API**: sends the RAG to DeepSeek, OpenAI, or any endpoint compatible with the OpenAI format. Requires an API key and an endpoint URL. Suitable for more capable models or team environments.

```python
def generate(self, rag_context: str, query: str, error_context: str = "") -> str:
    system_prompt = (
        "You are an assistant specialized in code generation. "
        "You are provided with structured context extracted from a conceptual graph. "
        "Use ONLY the APIs present in the context."
    )
    user_content = rag_context + "\n\n"
    if error_context:
        user_content += f"PREVIOUS ERROR (correct this):\n{error_context}\n\n"
    user_content += f"Request: {query}\n\nCode:"
    ...
```

The `error_context` parameter is the correction loop mechanism: if the sandbox fails, the error message is reinserted into the prompt for the next generation. It is not intelligence — it is automation of a rule-guided trial-and-error cycle.

## Sandboxed verification

The generated code is executed in an isolated subprocess before being returned to the user. The verifier implements an explicit block of dangerous patterns — `os.system`, `subprocess`, `eval`, `exec`, file write operations — before any execution.

```python
def verify_and_correct(self, code, language, query, rag_context, llm_connector):
    current_code = code
    for attempt in range(1, self.max_attempts + 1):
        result = self._run_in_sandbox(current_code, language)
        if result["success"]:
            return SandboxResult(success=True, code=current_code, attempts=attempt)

        error_context = (
            f"The following code produced an error:\n```\n{current_code}\n```\n"
            f"Error:\n{result['error']}"
        )
        # Correction loop: same pipeline, new attempt with error in context
        current_code = llm_connector.generate(
            rag_context=rag_context, query=query, error_context=error_context
        )
        current_code = self._extract_code(current_code, language)
    ...
```

The loop uses the same RAG context from the original fetch — the fetch is not re-executed — and adds the error as additional context. If after `max_attempts` the code does not pass the sandbox, it is returned with an explicit warning to the user.

## Building the graph from a GitHub repository

The manually built seed graph demonstrates the mechanism, but raises an inevitable question: how does one build a real graph from an existing codebase, without writing every node by hand?

`github_builder.py` answers this question using exclusively the GitHub REST API — no local clone, no additional dependencies beyond `requests` already in the project. The pipeline has five phases.

**Fetching the tree.** A single call to `/git/trees?recursive=1` returns the entire repository tree in JSON. This is more efficient than traversing folder by folder and requires no authentication for public repositories, though a GitHub token (configurable in the interface) raises the rate limit from 60 to 5,000 requests/hour.

**Filtering.** Files are selected by extension (`.js`, `.ts`, `.py`, `.jsx`, `.tsx`) and path — `node_modules`, `dist`, `build`, and similar folders are excluded. Test files are discarded, because they contain specific usage examples, not API definitions. If the repository exceeds the configured file limit, files in the root and in `src/` and `lib/` folders are prioritized.

**Regex-based extraction.** For JavaScript and TypeScript, the builder extracts exported functions (`export function`, `export const = () =>`), classes, TypeScript interfaces, and `module.exports`. For Python, it extracts public functions and classes with their docstrings. JSDoc comments are paired with the following functions, so the signature and documentation end up in the same node. This is not Tree-sitter — it is more fragile on highly idiosyncratic code — but it covers the vast majority of well-structured repositories without additional dependencies.

**Categorization by path.** The path structure of a repository is already semantically rich. `middleware/logger.js` almost certainly contains logging middleware; `routes/users.js` contains user routing; `auth/jwt.js` contains authentication. The builder maps the path to the semantic field using a priority-ordered list of patterns. The entity name refines the categorization if the path is insufficient. Intersections are inferred from terms present in the docstring.

**Relation inference.** Once all nodes have been produced, the builder reconstructs structural relations: hierarchy by path (a node in `middleware/` is `part_of` the `middleware` node), `related` relations between nodes in the same semantic field, `intersects` relations toward nodes in the declared intersection fields. Each relation references the destination node by UUID — not by `node_id` — exactly as in the manually built graph. The `node_id` is used during construction as a lookup point for resolving references between nodes within the same import session, but what is written in `relations` is always the `target_uuid` of the destination node.

**Structure of the extracted node.** Each node produced by the builder has the same structure as the manually built graph: `uuid` automatically generated by `make_stable_layer()`, `node_id` derived from the path and the name of the extracted entity (e.g. `"middleware.logger"`), and all stable layer fields. The extracted `node_id` is the readable entry point that the human reads in the preview and uses to identify what is being imported; the UUID is the key the system will use for all subsequent operations. Once imported, the node is indistinguishable from one built by hand — the system does not know or remember its origin.

The flow in the interface is intentionally two-phased. After analysis, the system shows a preview of the extracted nodes with their field, type, and prototypicality — the human can read what would enter the graph before it enters. The nodes are written to a staging file; only after explicit confirmation are they imported into the graph and the vocabulary regenerated. This is the human control point over the graph's outward expansion: the network grows by decision, not by automation.

A test on a sample of real code — a `requestLogger` function with JSDoc, an `authenticate` arrow function, a `Router` class — produces nodes with the correct semantic field, keywords extracted from the name and signature, and relations inferred from the path hierarchy. Categorization is imperfect on unstructured code or code with non-standard conventions, but on well-organized repositories — which are also the most useful ones as sources — it works without requiring node-by-node supervision.

## The interface: five sections, explicit human control

The interface is a static HTML file that communicates with the backend via REST API. It is designed to make every phase of the flow visible and to give the human an explicit intervention point at every structural step.

**Step 1 — Query**: the user writes the request in natural language. The system translates the query into instances and shows them before starting any navigation.

**Step 2 — Instances**: the user sees the identified instances, can remove some, add others manually by node_id, and only then confirm the start of the fetch. This is the structural control point: the fetch does not start without confirmation.

**Step 3 — Fetch**: after navigation, the system shows the collected pool, the textual structured RAG, the abandoned paths, and the new episodic links created. The "Abandoned paths" panel is operational transparency: it shows exactly which paths the system evaluated and discarded.

**Step 4 — Generation**: the generated code appears with the sandbox outcome (green if verified, amber if not verified), the number of attempts, and a copy button.

The **Graph** panel shows all nodes with their details (stable and episodic layers expandable) and includes the episodic pruning button — the maintenance operation that removes links never reused.

The **Import from GitHub** panel manages the graph construction pipeline from external repositories: fields for owner, repo, branch, path filter, and token; preview of extracted nodes; explicit confirmation before import. The graph does not expand until the human approves the preview.

## What the prototype shows — and what it does not

The prototype demonstrates that the mechanism works: the symbolic translation correctly identifies instances on a restricted domain, the fetch stops at pertinent boundaries without exhaustively exploring the graph, the produced RAG is structured and readable, the end-to-end pipeline from query to code is complete. The GitHub builder adds the ability to expand the graph from real repositories without building every node by hand.

It does not demonstrate scalability. Twelve nodes are a controlled domain. A real graph for "Next.js 14 + TypeScript + Prisma" built from official repositories would have hundreds of nodes and thousands of relations — and the behavior of the fetch on that graph requires empirical testing that this prototype does not provide. The builder can produce those nodes, but calibrating the fetch on a larger graph is work yet to be done.

It does not demonstrate code generation quality. Quality depends on the chosen language model and the precision of the RAG: a correct RAG reduces the error space, but does not eliminate it. The sandbox correction loop helps intercept execution errors, not subtle semantic errors.

The builder's regex-based categorization works well on well-structured repositories and less well on codebases with non-standard or heavily dynamic conventions. It is not a substitute for full AST parsing — it is a practicable approximation for a prototype, one that requires human review of the preview before import.

These are not defects to be corrected in future versions: they are the honest limits of what a prototype of this kind can demonstrate.

## The symbol as a statistical object: stable layer, episodic layer, and centroid updating

The prototype implements the episodic layer as an accumulator of contextual connections, each identified by `target_uuid` and weighted by a `use_count`. This structure is correct as a starting point, but incomplete with respect to what the symbol should do in a mature system: not only recording which nodes are reached during navigation, but tracking how strongly each traversed symbol is associated with this one — and using that distribution to update the field's centroid and the `label` array together.

### Weight, distribution, and distance — all within the label

A clarification on what weight measures in this system: a node's `use_count` is not incremented when the node is selected as an initial instance, nor when the fetch encounters it and discards it as irrelevant. It increases only when the node is **traversed and processed** — included in the pool because the fetch found it pertinent to the current query. This distinction matters: the weight distribution in the `label` does not reflect how often a node has been mentioned in queries, but how often it has proven relevant when the system navigated through it. It is a measure of processed relevance, not of surface frequency.

The `label` array accumulates, for each symbol, the set of symbols that have reached it through traversal, each with this processed weight. Together, they constitute a distribution over the traversed symbols. Distance from the centroid is read directly from this distribution — not computed in an external embedding space. A symbol that traverses this node with high weight is close to the centroid: it is a frequent, defining context. One with low weight is peripheral: it has touched the node, but rarely enough that it does not shape its field. No external embeddings are required. The human confirmation of instances before the fetch already provides the domain filter — the exploration starts from a semantically coherent set chosen by the human, and the weights accumulate within that boundary. The distribution that emerges is therefore already meaningful without needing external grounding.

Weight and position in the distribution are two readings of the same internal data: weight is processed activation frequency; position in the distribution relative to the dominant traversing symbols is the operational definition of distance. Both are needed: weight governs pruning and promotion; position in the distribution governs centroid recalibration and field boundary determination.

### The centroid and its updating

Each symbol has a centroid in the graph — its position in the semantic field, defined in training with human supervision. This centroid is not fixed forever: it shifts as the weight distribution of the `label` shifts.

The mechanism is self-contained. If the distribution converges stably around a set of traversing symbols different from those that defined the centroid in training, the centroid can be recalibrated by reading the dominant entries in the `label` and adjusting the node's field accordingly. No external computation is required. In the code domain, an additional feedback signal tightens the loop further: when the generated code is tested in the sandbox, the outcome — success or failure — retroacts on the search queries, refining which instances to activate in future navigations. The system corrects its entry point based on verifiable results, not on statistical drift alone.

This updating happens **in batch**, not in real time. Continuous updating would make the symbol dependent on query order, destroying its stability as a reference point. The recalibration is periodic maintenance: the system accumulates evidence; the operator — or an automated agent triggered by statistical divergence — decides when to run the recalculation. The centroid and the `label` array are updated **in the same operation**: the centroid records *where* the node sits; the `label` records *what* it has proven to be. Updating one without the other would produce an internal inconsistency that corrupts both fetch navigation and field boundary determination.

Episodic layer pruning accompanies the recalculation: links with `use_count` below threshold are removed; frequent ones become candidates for promotion to the stable layer or direct integration into the graph as new nodes.

### Plurimodal distributions and node splitting

In open domains, the weight distribution of a symbol's `label` can be plurimodal: several distinct traversing symbols with similar weights and no dominant center. When this happens, shifting the centroid toward an average would be misleading — the node is not drifting, it is being used in genuinely distinct ways. The batch operation should recognize this pattern and flag the symbol as a candidate for splitting into two or more distinct nodes, each anchored to one of the peaks in the distribution. This decision belongs to the human supervisor: the system surfaces the evidence; the human decides whether to split, merge, or leave unchanged. Node splitting is the mechanism by which the graph grows in precision guided by actual usage, not by arbitrary expansion.

### A special case: code

In the programming domain, centroid updating is in practice irrelevant, and the reason is structural rather than incidental. A symbol like `express.middleware` corresponds to a precise, unambiguous concept: every query that reaches it does so in the same semantic context, and no traversing symbol will ever accumulate enough weight to shift the centroid. The distribution is stable by definition. What does evolve in this domain is not the centroid but the quality of entry: the sandbox feedback loop refines the search queries over time, so the system reaches the right nodes more directly with each iteration. The field stays fixed; the path to it improves.

### Multiple access points and dormant graphs

The most important consequence of this architecture is that the graph remains static, ordered, and verifiable — but access to it multiplies with use. Each user, each specialized domain, each project accumulates in the symbols' episodic layer its own configuration of connections and weights: in effect, its own *access point* to the graph. Two users employing the same system for different purposes will activate the same nodes but via different episodic paths, and over time will see the system respond with structurally different RAGs while starting from the same base graph.

This property becomes operationally significant when the system is used across projects involving different technology stacks. A Django + React project requires the Django, React, Python, and JavaScript graphs. But Python and JavaScript are generic graphs — their symbolic layer is rich and stable. Django and React are the project's specialized graphs. The solution is *not to load everything together*: Django and React are activated as primary graphs; Python and JavaScript remain dormant, accessible only if an active symbol calls them through a link pertinent to the current query. This "awakening" is exactly the progressive fetch applied to symbols rather than nodes: a dormant symbol is activated because it is related to an already-active one, and navigation extends only if pertinence justifies it.

When the project changes — from Django + React to FastAPI + Vue, for instance — the episodic layer of the Django and React symbols can be suspended or archived, and the FastAPI and Vue symbols' layer is loaded. The underlying graph does not change: what changes are the access points. This is the mechanism that makes the architecture suited to specialized use without requiring the construction of a separate system for each domain.

## Startup instructions

```bash
# 1. Clone and install dependencies
pip install -r requirements.txt

# 2. Start (builds the seed graph on first run)
python run.py

# 3. Configure the model in the interface (Configuration tab)
#    — Local: install Ollama and download deepseek-coder
#    — Remote: enter URL and API key

# 4. Rebuild the graph from scratch if necessary
python run.py --rebuild-graph
```

The interface opens automatically in the browser. The server stays active until Ctrl+C is pressed.
