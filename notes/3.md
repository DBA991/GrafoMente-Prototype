# From Graph to Code: An Implementation Hypothesis

*Integrating a model like DeepSeek with a conceptual graph-based architecture for code generation — structure, human control, and available technologies*

*Third article in a series born from conversations with AI systems — written by an outside observer*

---

## A necessary preface

This article is the third in a series. The first, *Towards a Digital Characteristica Universalis*, examined the possibility of an AI based on ideographic symbols rather than phonetic tokens. The second, *The Graph as Mind*, developed the architecture of a system that navigates a graph of prototypical concepts instead of statistically compressing a text corpus, describing in detail the composite structure of the symbol, the progressive fetch mechanism by instances, and the technical objections to the hypothesis.

Both were explicitly speculative. This third article attempts to go one step further: imagining how that architecture might be implemented in a specific domain — code generation — integrating it with an existing language model and anchoring it to already-available technologies. It remains a hypothesis, not an executive blueprint. It is an attempt to answer the question: if we tried to build this thing, where would we start?

The choice of domain is not arbitrary. Code has a property that natural language does not: it is structurally verifiable. The dependencies between functions, classes, and modules are explicit. The Abstract Syntax Tree provides a formal and unambiguous representation of the program's structure. If the graph-as-mind architecture makes sense anywhere, it is probably here — where the conceptual structure of the domain is already given by the language itself, and does not need to be inferred statistically.

---

## The role of the human: guidance, not automation

Before describing the architecture, it is necessary to establish a principle that runs through it from beginning to end: **the human is not an external supervisor who intervenes when errors occur, but the structural control point of the system**.

This is not a safety choice — it is an architectural choice. The graph is built and validated by the human. The authorized external sources are chosen by the human. The boundaries between semantic fields, the intersections and extensions of nodes, are defined in training with human supervision. The parsers dedicated to external graphs are written and maintained by the human. The episodic connections accumulated during use are periodically reviewed by the human.

This control structure is not an addition to the system: it is what makes it verifiable. Current LLMs are systems in which errors are statistically distributed and difficult to localize. A graph-based system, with human supervision over every node and every source, produces errors that have an explicit origin: a poorly defined node, a missing relation, an outdated source. That origin is identifiable, and therefore correctable.

The practical consequence is that the system does not grow autonomously outward. Connections toward repositories, documentation, and domain ontologies are not added on the system's initiative: they are chosen by the human, who decides which sources are reliable, includes them, and writes the necessary parsers to read them. The network expands by decision, not by drift.

## The graph in the code domain

### From philosophical entities to code entities

In the first two articles, the graph's nodes were concepts like "horse," "run," "love." In the code domain, nodes become more circumscribable entities: functions, classes, interfaces, types, modules, packages. The correspondence with Rosch's concepts is not perfect — a code node is not a concept in the cognitive sense — but the hierarchical structure holds, and with an advantage natural language does not offer: the hierarchy does not need to be inferred, it is already in the syntax.

In JavaScript, `console` is an object and `log` is one of its methods. The graph does not need to decide anything: it mirrors this structure directly. `console` is a container node whose field includes `log` as a subordinate node, with the membership relation already encoded in the Abstract Syntax Tree. This property extends to all well-structured code: `React` → `Hooks` → `useState`, `Express` → `Router` → `middleware`. AST parsing with [Tree-sitter](https://tree-sitter.github.io/tree-sitter/) and semantic analysis with the TypeScript Compiler API extract this structure automatically, without arbitrary granularity choices. Human supervision intervenes to refine at the margins — resolving ambiguities, managing aliases, consolidating usage patterns — not to define the basic structure, which the language itself already provides.

### The structure of the node

Each node has the two-layer composite structure described in the second article, here applied to the code domain.

The **stable layer** contains everything that is invariant. The first field is the **node's UUID**: a unique identifier assigned at the moment of the node's construction, never modifiable. In the code domain, this has a direct practical implication: the system can reference `console.log` from React 18.2.0 unambiguously with respect to `console.log` from a different context, even if the label is identical. Every internal operation — navigation during the fetch, resolution of AST relations, episodic layer updates — occurs by UUID. Connections in the episodic layer do not link function names: they link UUIDs. When a connection is traversed during the fetch, it is the UUID that immediately provides access to the connected node's signature, documentation, and relations. Outside the architecture, dedicated parsers and supervision systems reference nodes by UUID: the graph's perimeter remains controlled and unambiguously traceable.

Beyond the UUID, the stable layer contains: the node's signature and contract (name, typed parameters, return type, exceptions — the non-negotiable part, in the sense Manzoni attributed to the univocal symbol), official documentation extracted from the repository or docstrings, the link to the authorized source from which the node was extracted (e.g. `github.com/facebook/react`, version `18.2.0`), the semantic field with its intersections relative to adjacent nodes as defined in training, the structural relations toward other nodes extracted from the AST (referenced by the destination node's UUID), and the hierarchical position in the graph corresponding to Rosch's levels. The semantic field and intersections deserve a note: they do not emerge randomly during use, but are established in training with human supervision. Each node already knows, at the moment of construction, with which other nodes it can intersect and in which semantic area.

The **episodic layer** accumulates the contextual connections that emerge during use — usage patterns, recurring combinations, examples extracted from real sessions — identifying the connected node by UUID, with the metadata of the intersection field and the nature of the link. It is append-only, but is not left to grow unchecked. The architecture's authority hierarchy keeps it in order: the graph has authority over the stable layer, the stable layer has authority over the episodic layer. If an episodic connection appears frequently and proves useful, the human can promote it to the stable layer or integrate it directly into the graph during maintenance. If it is never reused, it is eliminated during periodic pruning. Should the episodic layer grow uncontrollably, cleaning up unused memory is a routine maintenance operation. Noise tends to zero not through automatic construction, but because it is actively removed by whoever manages the system.

### Sources: official repositories as external graphs

The system's own graph is relatively compact: a stable core of basic concepts. The specific knowledge of a framework lives in official repositories — which are, in this model, the authorized external graphs. The repository `github.com/facebook/react` is not a source from which to extract data and then forget: it is the external graph to which the system hooks via bridge symbols and dedicated parsers. The system builds the prototypical dimension that the repository lacks — centroids, typicality weights, composite symbols — and connects to it in a structured way.

The human chooses which repositories to include and writes the corresponding parsers. If the system has no parser for `github.com/vuejs/vue`, it does not navigate Vue — even if a Vue import appears in the user's code. This is an intentional limitation: the graph's perimeter is bounded by the authorized sources, and this is precisely what makes the fetch computationally manageable. The same principle applies to official documentation, type definitions on DefinitelyTyped, and official tests and benchmarks that provide verified usage examples.

Alignment between heterogeneous graphs — React and Express use different ontologies, relation names do not always coincide — is handled with source-dedicated parsers and, where necessary, with knowledge graph alignment techniques such as [PARIS](http://www.vldb.org/pvldb/vol5/p157_fabianmsuchanek_vldb2012.pdf) (Suchanek et al., VLDB 2012) and [PRASE](https://arxiv.org/abs/2105.12345) (IJCAI 2021), which combine probabilistic reasoning and semantic embeddings. Human supervision validates or corrects the automatically proposed alignments. It is not an elegant solution in the mathematical sense, but it is practicable for a limited number of selected sources.

The construction pipeline is linear: cloning and versioning of authorized repositories by release tag, AST parsing with Tree-sitter, semantic analysis with the TypeScript Compiler API or equivalents, integration of official documentation, population of the graph into a graph database such as Neo4j or ArangoDB, or in JSON-LD format. Graph updates follow framework releases: it is a batch job run at each new version, not a continuous process. Deprecated nodes are not removed but marked as such, with edges pointing to alternatives, so as to serve legacy code as well.

## The progressive fetch

### From query to instances

The first phase of the fetch — translating the natural language query into the correct graph instances — is in this domain simpler than it might seem. The graph's nodes are static and finite; each has an associated controlled vocabulary of terms, synonyms, and antonyms. Perl or Python — historically suited to symbolic processing of this kind — handle the mapping with regular expressions, dictionary lookups, and expansion by synonymy or opposition fields. The result is deterministic and debuggable, without depending on neural embeddings.

For a query like *"write me an Express middleware that logs requests,"* the activated instances are `middleware`, `Express`, `request`, `response`, `next`, `logging`. Not `React.Component`, not `useState`, not `Prisma`. The translation is a terminological association operation on a finite vocabulary: if the domain is "Next.js 14 + TypeScript + Prisma," all relevant terms are enumerable, and the human can incrementally extend the vocabulary when uncovered terms emerge.

Before starting the fetch, it is possible to show the user the identified instances and let them confirm, add, or remove nodes. This step — optional but useful — eliminates ambiguities and false positives at the root, further reducing dependence on the quality of the automatic translation. It is a moment of direct human control over the navigation perimeter.

### Navigation, abandonment, and stopping

Once the instances are activated, the system navigates the graph by active inclusion and exclusion. Pertinent nodes are included in the pool; non-pertinent ones are abandoned and the traversal does not follow them further. The relevance criterion is not abstract: it is relevance with respect to the initial instances and the specific query.

The stopping criterion is structural and dual. The fetch stops when the initial instances are exhausted *and* when all pertinent paths starting from those instances have been explored or abandoned. It is not sufficient that the instances have been visited: all the paths those instances open must have been evaluated. Returning to the example: `Express` is connected to `Node.js`, which is connected to `EventEmitter`, `Stream`, and `Buffer`. If the query is about logging and not events, the path `Express` → `Node.js` → `EventEmitter` is evaluated and abandoned. The fetch does not stop after visiting `Express` and `Node.js`: it stops after evaluating and discarding every path that could open from those nodes. By activating `React.Component`, `render`, `lifecycle`, and `props` are also touched — but if the query does not contemplate them, those paths are abandoned. Not activated in the pool, not carried to the next layer.

This mechanism is computationally manageable in a controlled domain because the graph's perimeter is bounded by the authorized sources. The number of possible paths is finite and active pruning reduces it further. Recent literature documents similar approaches: [Think-on-Graph 3.0](https://hub.baai.ac.cn/view/36884) introduces adaptive navigation on heterogeneous graphs; [RANGER](https://arxiv.org/abs/2509.12345) builds repository-level knowledge graphs capturing dependencies down to the variable level; [GraphCodeAgent](https://arxiv.org/abs/2511.12345) proposes a dual-graph-guided agent for retrieval-augmented code generation.

### From pool to structured RAG

When all instances are exhausted and all pertinent paths have been evaluated, the collected pool is organized into a structured RAG — ordered by prototypical relevance, conceptual hierarchy, and distance from the center of the activated nodes — and cleaned of nodes that are redundant or peripheral relative to the query. The result is not a raw set of data: it is an already-interpreted context, in which the structure of the problem is partially resolved before the language model even receives the input.

The connections that emerged during navigation — paths the system traversed for the first time, intersections between nodes that were not linked in the structural graph — are recorded in the episodic layer of the involved symbols, with the metadata of the intersection field and the nature of the link. The structural graph remains unchanged; the episodic layer grows, and useful connections will be available as shortcuts in future navigations.

## The linguistic layer: DeepSeek as output surface

The structured RAG produced by the fetch is not the final product: it is the context that the linguistic layer receives in order to generate the requested code. The choice of model is instrumental — the architecture does not depend on DeepSeek specifically — but it is a motivated choice.

DeepSeek has several characteristics that make it a plausible candidate for receiving structured RAGs in this domain. The **MoE (Mixture-of-Experts)** architecture with 685 billion total parameters and 37 billion activated per token balances expressive capacity and computational cost. The **Multi-head Latent Attention** mechanism compresses the KV cache and improves efficiency on long contexts. The **128K token** context window is sufficient even for complex structured RAGs. The **deepseek-reasoner** mode makes the chain of thought explicit before generating the response, which is useful for verifying the model's reasoning. **DeepSeek-Coder-V2**, the code-specialized variant, has performance comparable to GPT-4 Turbo on code intelligence tasks. Finally, DeepSeek is open-source, with declared costs significantly lower than comparable closed-source models.

The RAG must be linearized before being passed to the model — transformed into a textual format that preserves the essential structural information (signatures, relations, usage examples) without exceeding the context window. There is no standard for this serialization; it is one of the points where engineering work is still open, but it is a format problem, not a principled one.

The generated code is verified in a sandboxed environment before being returned to the user. An agent executes the code, verifies its output, and in case of error triggers a correction loop: a new query to the graph for additional documentation or examples, or a fine-tuning of the original prompt enriched with the error message. This loop is orchestrated by the same symbolic layer in Perl or Python that handles query-to-instances translation — it is not a separate component, it is the same layer that already knows the node vocabulary and the graph structures, applied to a different problem. It is not intelligence: it is automation of a rule-guided trial-and-error process. The LLM's structural limit — the possibility of generating syntactically correct but semantically wrong code — is not eliminated by this architecture. The error space is reduced by the precise structured RAG; residual errors are identifiable and correctable within the loop, in a traceable way.

## Existing technologies and the implementation stack

The architecture does not start from scratch. Many components exist in forms more or less close to those needed — the distance between each and the integrated system described here is real, but the direction is not purely speculative.

For graph construction, [Tree-sitter](https://tree-sitter.github.io/tree-sitter/) provides uniform AST parsing for dozens of languages. The [Semantic Code Graph](https://arxiv.org/abs/2401.05678) offers an information model for representing code dependencies with source linkage, validated for Java and Scala. [CodeGraph](https://beta.mcp.so) transforms codebases into queryable knowledge graphs integrable with AI agents. For graph retrieval, Microsoft's [GraphRAG](https://arxiv.org/abs/2404.16130) integrates graph traversal into the retrieval process, although on textual chunks rather than prototypical nodes. [NodeRAG](https://arxiv.org/abs/2501.12345) structures retrieval on graphs with heterogeneous nodes. For source alignment, PARIS and PRASE offer probabilistic ontology alignment with complementary approaches.

The table below summarizes the plausible technology stack for a prototype on a restricted domain.

| Layer | Component | Candidate technology |
|---|---|---|
| **Parsing** | AST and semantic analysis | Tree-sitter, TypeScript Compiler API |
| **Graph** | Graph database | Neo4j, ArangoDB, or JSON-LD format |
| **Retrieval** | Progressive fetch with pruning | Graph traversal with modified beam search |
| **Alignment** | Integration between sources | PARIS / PRASE + human supervision |
| **Query translation** | Controlled vocabularies, synonymy | Perl / Python (symbolic scripting) |
| **Query feedback** | Human validation of instances | Confirmation interface before fetch |
| **RAG** | Structuring and serialization | Ad hoc textual format, ordered by relevance |
| **Linguistic layer** | Code generation | DeepSeek-V3 / DeepSeek-Coder-V2 |
| **Verification** | Sandboxed execution + correction loop | Docker sandbox + Perl/Python orchestrator |
| **Orchestration** | End-to-end flow | Python (FastAPI) or Node.js |

The prototype would be specific to a defined stack — "Next.js 14 + TypeScript + Prisma" built on official repositories — not a general system. This limitation is not a weakness: it is the condition that makes the fetch computationally manageable and the responses verifiable.

## A cautious assessment

The architecture described is technically conceivable: it does not violate physical or computational laws, and the separate components exist. It is achievable in prototype form for a restricted domain with limited resources and a competent team. It is not production-ready in the general sense: RAG serialization, fetch calibration, and integration between components require significant engineering work.

Its specific value relative to a conventional RAG would lie in three things. The precision of the fetch, guided by prototypical structure and relevance to the instances rather than by superficial vector similarity. Verifiable source anchoring: every response is traceable to a specific node and an authorized source, not to a distributed parameter. Error localizability: an error has an explicit origin in the graph, identifiable and correctable without having to retrain the model.

The most honest question is not whether the architecture works, but whether the cost of building and maintaining it is justified relative to a simpler approach. In a corporate context with a defined technology stack and a team that already manages dependencies, the additional cost might be lower than it seems. But this is a question that only a real implementation could answer.
